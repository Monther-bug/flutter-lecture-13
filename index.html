Idea 1 · Use what we know

Lifting state up

  • ProductsPageowns _cartCount (lifted up here)
    • appBar:AppBar
      • CartBadge(count)↓ data goes down
    • body:ProductList(onAdd)↓ callback goes down
      • ProductTile(onAdd)↑ event goes up: onAdd() → setState
  1. Find the closest common parent of every widget that needs the data
  2. Move the data and setState into that parent
  3. Pass data down as constructor parameters
  4. Pass callbacks down; children call them to send events up
A callback is just a function we hand to a child, like onPressed in Lecture 07.
Mobile App Development · Lecture 15

A callback is just a function we hand to a child, like onPressed in Lecture 07. The child does not know what happens; it only calls the function.

Built into Flutter · no package

Flutter's own tool: ValueNotifier + ValueListenableBuilder

lib/cart_count.dart · lib/cart_badge.dart
// cart_count.dart: one place for the data
final ValueNotifier<int> cartCount = ValueNotifier<int>(0);

// Change it from anywhere: cartCount.value++;
// Listen to it inside build() (cart_badge.dart):
ValueListenableBuilder<int>(
  valueListenable: cartCount,
  builder: (context, count, child) {
    return Badge.count(
      count: count,
      isLabelVisible: count > 0,
      child: const Icon(Icons.shopping_cart),
    );
  },
)
1ValueNotifier: one placeholds one value and notifies listeners when .value changes
2Change it from anywherecartCount.value++; in any button, on any page
3ValueListenableBuilder: listenre-runs only its builder when the value changes
A top-level (global) variable is fine for this demo. In Lecture 16, Provider gives us a cleaner way to share it.

The landscape

State management packages: an overview

PackageMain ideaLearning curveGood for
ProviderproviderChangeNotifier classes placed above the widgets; widgets watch or read them. Built on InheritedWidgetEasySmall and medium apps, beginners; used in the official Flutter docs
Riverpodflutter_riverpodProviders declared outside the widget tree, read with ref; strong support for data that arrives later (loading and error states). Same author as ProviderMediumMedium and large apps, lots of data from the internet, testing
Bloc / Cubitflutter_blocThe UI sends events (Bloc) or calls methods (Cubit); new states come outMedium to high(more code)Large apps and teams that want a strict, predictable structure
GetXgetAll-in-one: reactive variables (.obs + Obx), navigation, dependency injectionEasy to startQuick prototypes and small apps; it changes how you do many Flutter things, so the whole team should agree on it
MobXmobx + flutter_mobxObservables, actions and reactions; uses code generationMediumDevelopers who already know MobX from JavaScript

Others: Redux (flutter_redux), Signals (signals), and many more on pub.dev under the topic “state-management”.  Highlighted: our pick, Lecture 16
